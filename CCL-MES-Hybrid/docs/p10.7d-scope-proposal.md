## Scope at a glance

7d delivers the IPQC + QA Approval surface — the operator-facing
review gate between SETTING and RUNNING. Today's 7c stack ships a SQL
shim for `IPQC_WAIT → IPQC_APPROVED` in `checkpoint-7c-2.sh` /
`checkpoint-7c-final.sh`; 7d replaces that shim with a real wire +
dashboard.

| Phase transition | Owner | Comes from 7c | Lands in 7d |
| --- | --- | --- | --- |
| `SETTING → IPQC_WAIT` | OP via `/setting/done` | ✓ (7c-2) | (unchanged) |
| `IPQC_WAIT → IPQC_APPROVED` | QC via judgment "Go Run" | shim in checkpoint scripts only | **wire** |
| `IPQC_WAIT → PREPRESS` (reset) | QC via judgment "Stop Line" | n/a | **wire** |
| `IPQC_WAIT → QA_PENDING` | QC via judgment "Special Accept" + reason | n/a | **wire** |
| `QA_PENDING → IPQC_APPROVED` | QA via "Approve" | n/a | **wire** |
| `QA_PENDING → PREPRESS` (reset) | QA via "Reject" | n/a | **wire** |
| `IPQC_APPROVED → RUNNING` | OP via `/run/start` | ✓ (7c-2) | (unchanged) |

## Open questions (each with Recommended + trade-off)

### Q1 — Print check criterion source: hardcoded vs `qc_criterion` per product family?

**SpecHub citation** (line 130): *"3 items (cấu hình được per product
family qua `qc_criterion`): Check A: Color (default ΔE ≤ 2), Check B:
Registration, Check C: Content."*

**Recommended**: **Hardcode 3 check slots (A/B/C) in domain entity +
defer the per-product `qc_criterion` lookup to 7e**. The 3 slots
themselves are a wire-stable contract (always exactly Color +
Registration + Content); only the THRESHOLD per check (e.g. ΔE ≤ 2 vs
ΔE ≤ 3 for a specific customer) needs the per-family override. 7d
ships with hardcoded thresholds; 7e brings them in alongside the FQC
dashboard which has the same shape.

**Trade-off**: ✓ ships the operator-facing review gate this sprint
(unblocks production go-live without IPQC paper). ✗ a future customer
that needs a non-default ΔE threshold must wait for 7e — but the
override is a configuration enhancement, not a workflow blocker. ✗
hardcoded thresholds drift if SpecHub adds checks D/E later — but
that's a coordinated schema change anyway.

**Contract gap if rejected**: domain entity needs a polymorphic
shape (or a `Dictionary<string, IpqcCheckRow>`) which complicates
audit JSON + 7e's eventual lift.

### Q2 — Domain entity shape: per-row table vs single row with N status fields?

**Background**: SpecHub §3 mentions an `ipqc_checks` table
(line 210: *"IPQC | Material + 3 print checks + judgment + QA
approve"*) — but that's PostgreSQL design from a different stack. For
EF/SQLite + the L11-aware pattern we already have, either shape works.

**Recommended**: **Single `WoIpqcCheck` row with 4 status fields
(`MaterialStatus` / `PrintAStatus` / `PrintBStatus` / `PrintCStatus`)
+ 4 NG fields (`MaterialNgReason` / `PrintANgReason` / …) + judgment
fields (`Judgment` enum + `SpecialAcceptReason` + `QaApproveBy` +
`QaApproveAt`) + RowVersion**. Mirrors `WoPlateCheck` / `WoCutterCheck`
1:1 pattern from 7b. Aggregate rollup (`IsReadyForJudgment` — all 4
sets OK or NG with reason) computed in pure helper, parallels
`MaterialsReadinessRollup` from 7b.

**Trade-off**: ✓ keeps the 7c rollup-race pattern intact (single WO
touch on each PUT, single SaveChanges, SQLite write-lock serialises).
✓ matches the 7b 1:1 entity shape operators already learned. ✗
diverges from SpecHub's per-row table — but the FQC / OQC dashboards
will adopt the same 1:1 shape so the project converges on a
consistent EF pattern. ✗ adding a check D/E later requires a
migration ADD column (vs SpecHub's INSERT row) — but that's fine for
~yearly schema additions.

**Contract gap if rejected**: per-row table = `WoIpqcCheckRow` with
`CheckSlot` enum (Material / PrintA / PrintB / PrintC) + 4 child
rows per WO instead of 1; more boilerplate per PUT (lookup-by-slot,
upsert), less skim-readable in audit detail JSON.

### Q3 — Role gate: separate `Qc` + `Qa` roles vs single `Qc` role with QA Approve permission?

**SpecHub citation** (line 196-197):
> | `qc`  | ✗ | ✗ | ✓ | ✓ | ✗ | Default QC chỉ IPQC; cần escalate QA |

SpecHub uses one `qc` role with both IPQC + QA capabilities. The
"escalate QA" wording suggests a separate sign-off step, not a
separate role.

**Recommended**: **Reuse the existing `UserRole.QC` role for both
IPQC + QA Approve, but require a SECOND user for QA Approve**
(separation-of-duty: the operator who marked SPECIAL_ACCEPT cannot
also QA-approve it). Server enforces "QA approver ≠ IPQC submitter"
in the controller; client UI shows the second-operator login modal
inline.

**Trade-off**: ✓ no new role enum value, no migration to
`UserRole`, no Account UI rewire. ✓ separation-of-duty is exactly
the compliance posture customers expect for "special accept" cases
(matches IATF 16949 + IFS audit requirements). ✗ requires
session-level guard (impersonation block) — easy to test
(`WoIpqcController.SpecialAcceptOnly` xUnit fixture asserts the
guard fires). ✗ doesn't model "QA Manager > QC Inspector"
hierarchy explicitly — defer to a future `UserRole.QaManager` if
ops needs it. **Compromise alternative**: ship a feature flag
`OPS_IPQC_REQUIRE_DISTINCT_QA_APPROVER` defaulting true, so a
small-team plant (1 QC inspector total) can disable the dual-sig
in dev/UAT.

**Contract gap if rejected**: new role enum + migration + Account UI
+ permission matrix expansion → 1-2 day sprint addition; deferring
to 7e would require holding 7d to "IPQC submission only, no judgment".

### Q4 — IPQC scope: tablet PWA inline vs Catalyst-only?

**Background**: SpecHub §3 mentions *"WebSocket push to tablet"* for
the IPQC notification (line 127) implying a tablet PWA. Today's
CCL-MES Hybrid is Catalyst-only.

**Recommended**: **Catalyst-only for 7d**. Same Razor pages, same
WorkOrders host. QC role logs into the Catalyst app installed on a
shop-floor tablet (operator's existing hardware). When SETTING done
fires, the QC operator sees the new IPQC_WAIT WO in their queue (or
scans the same QR). No new transport, no PWA build pipeline.

**Trade-off**: ✓ reuses 100% of the 7c-3 dashboard + Modal stack;
zero new infrastructure. ✓ matches today's hardware reality (each
shop-floor station has a Catalyst tablet). ✗ no WebSocket push —
QC must scan/manually look up the WO when SETTING is done. Mitigate
with a "WO inbox" sidebar widget showing IPQC_WAIT WOs (12-line
component, defer to 7d-3 if needed). ✗ tablet form-factor + Catalyst
window size — already handled by 7c-3 S9 responsive CSS, so this is
free.

**Contract gap if rejected**: WebSocket + PWA pipeline = 4-PR side
sprint (signal-R server + connection lifecycle + PWA shell + push
notification permission flow). Defer to a hypothetical 7g.

### Q5 — Photo evidence: required vs optional vs deferred?

**SpecHub citation** (line 290):
> Photo storage: presigned S3/MinIO URL trong NG modal — không upload
> qua main API

**Recommended**: **Defer photo evidence to 7e (alongside FQC)**.
7d ships text-only NG reasons (operator types free-form Vietnamese
prose, 1-500 chars, plus a reason code picker like 7b PREPRESS NG +
7c-2 NG-qty). Photo support requires presigned URLs, MinIO/S3 wiring,
+ CDN egress thinking — out of scope for the IPQC review gate proper.

**Trade-off**: ✓ ships 7d on the same day as 7c approvals if photo
is deferred (no new infra dependency). ✓ operator photo discipline
on shop-floor is paper-based today anyway (camera phone → printed
sticker), so digital photos are NICE-to-have not need-to-have. ✗
audit-trail completeness reduced — text reasons only; a customer-
complaint forensic could need photo. **Operational mitigation**:
QC operators upload photo to a shared folder + paste the path into
the NG reason text field (transition path, not a final answer).

**Contract gap if rejected**: presigned-URL backend + MinIO setup +
PWA-style upload from Catalyst (or system file picker integration)
+ a thumbnail viewer modal. Roughly 5-7 day sprint addition. Better
landed alongside FQC photo evidence in 7e for consistency.

### Q6 — IPQC notification: pull (operator polls) vs push (SSE) vs WebSocket?

**SpecHub citation** (line 127):
> IPQC nhận notification (WebSocket push to tablet)

**Recommended**: **Pull-only for 7d, sidebar widget refreshes every
60s** (same pattern as the existing scan-recent widget). IPQC_WAIT WO
queue rendered as a small list in the QC role's WorkOrders page. No
new transport. SSE / WebSocket deferred to 7g (same defer as Q4).

**Trade-off**: ✓ deterministic, no transport infra, no connection
lifecycle to manage. ✗ up to 60s latency between OP's `/setting/done`
and QC's queue update — acceptable given the typical 10-15 minute
IPQC review time (one minute lag at the start is invisible).

**Contract gap if rejected**: same as Q4 — WebSocket pipeline.

### Q7 — Judgment audit: single-row vs separate row per check + 1 judgment row?

**SpecHub citation** (line 218):
> action (enum): … IPQC_CHECK, IPQC_GO_RUN, IPQC_STOP_LINE,
> IPQC_SPECIAL_ACCEPT, QA_APPROVE_SPECIAL, QA_REJECT_SPECIAL

SpecHub has one `IPQC_CHECK` row + one judgment row, but it's
ambiguous whether each of the 4 check slots emits its own
`IPQC_CHECK` row or whether one combined row carries the 4 results.

**Recommended**: **One `WO_IPQC_CHECK` row per slot mutation +
one `WO_IPQC_JUDGMENT` row at the end**. Each PUT to update a check
slot emits one audit row with `detail.slot ∈ {Material, PrintA,
PrintB, PrintC}` + `detail.status` + `detail.ng_reason`. The
judgment POST emits a single `WO_IPQC_JUDGMENT` row with
`detail.outcome ∈ {GoRun, StopLine, SpecialAccept}` +
`detail.special_accept_reason` (if applicable). QA approve emits a
distinct `WO_QA_APPROVE` row with `detail.outcome ∈ {Approve,
Reject}` + `detail.qa_note`.

**Trade-off**: ✓ per-slot rows let forensic replay reconstruct the
exact sequence ("operator marked PrintA OK, then PrintB NG, then
Material OK, then judgment SpecialAccept"). ✓ matches the 7b
`WO_PREPRESS_MATERIAL_SET` / `_PLATE_SET` / `_CUTTER_SET` pattern
(operators already understand "one row per surface-element write").
✗ slightly noisier audit log — but 4 rows per WO at IPQC is
negligible vs the 5-15 row PREPRESS + 5-30 row RUNNING traffic
already accepted.

**Contract gap if rejected**: combined `IPQC_CHECK` row with
`detail.material_ok + detail.print_a_ok + …` flat fields → audit
search by "which slot failed?" requires JSON extract instead of
straight WHERE.

### Q8 — Migration baseline: separate 7d migration vs combine with 7e?

**Recommended**: **Separate 7d migration `AddIpqcReviewSurface`
(adds `WoIpqcChecks` table only)**. 7e will add `WoFqcSamples` +
`WoOqcChecks` in their own migration. This keeps each PR's
migration round-trip self-contained for verify-p10.7c.sh-style
Rule 6 self-prep.

**Trade-off**: ✓ verify script for 7d can Down to PREVIOUS = 7c
migration baseline + assert ONLY `WoIpqcChecks` appears post-Up. ✗
3 migrations vs 2 for the same overall scope — marginal cost; the
verify reproducibility benefit outweighs.

**Contract gap if rejected**: combined migration = harder to
isolate which table goes with which PR; merge complications if 7d
and 7e ship out of order.
