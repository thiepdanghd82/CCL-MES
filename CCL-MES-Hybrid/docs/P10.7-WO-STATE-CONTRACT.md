# P10.7 — Work Order State-Transition Contract

> **Status: DRAFT — awaiting Henry sign-off.** This document is the
> **BLOCKER for P10.7a** per the 3-codebase audit dated 2026-06-04
> (`docs/AUDIT-3-CODEBASES-2026-06-04.md` Phase C TL;DR, item 3 —
> "Biggest risk"). Until Henry signs §10, no PR labelled `P10.7*` may
> open against `main`.
>
> **Scope of this contract.** It LOCKS the server-authoritative state
> machine, transition matrix, audit emit shape, child-table write
> rules, concurrency guarantees, and recovery procedures for the MES
> 5-phase shop-floor flow. It DOES NOT lock the UI presentation
> (Razor pages vs WinUI), the persistence engine (SQLite vs SQL
> Server vs Postgres), nor the i18n key strings — those are free for
> the per-PR implementer to pick. The contract IS authoritative on:
>
> 1. The canonical state name set.
> 2. The legal transitions between them.
> 3. The events that trigger each transition.
> 4. The audit row emitted on each transition.
> 5. The child-table writes permitted in each state.
> 6. The concurrency token + Idempotency-Key contract that prevents
>    cross-shift / cross-operator corruption.
> 7. The recovery paths admins can invoke when a WO is wedged.
>
> **Why it exists.** Three codebases have three different state-shape
> models today:
>
> - **CCL-MES legacy** ships an 8-state `ProcessStepCode` enum + a
>   6-state `WoStatus` axis that move in parallel (`WorkOrderStateMachine.cs`
>   + `Enums.cs`). The transitions are guarded by both DB writes and
>   the `WorkOrderStateMachine.CanAdvance` C# matcher.
> - **SpecHub prototype** ships a 10-state `mes_status` enum
>   (`NEW → PREPRESS → SETTING → IPQC_WAIT → IPQC_APPROVED →
>   QA_PENDING → RUNNING → PAUSED → DONE → STOPPED`), enforced by
>   `mes_validate_transition()` plpgsql function + matching JS
>   `_mesTransition` in-memory state machine on the client. The HTML
>   prototype also surfaces 2 latent states `FQC_PENDING` /
>   `OQC_PENDING` + a terminal `SHIPPED` that the SQL migration does
>   not yet model.
> - **Hybrid current** reuses the legacy 8-state via project-reference
>   and only ships ONE write endpoint
>   (`POST /api/v1/work-orders/{id}/advance` → wraps
>   `WorkOrderService.AdvanceAsync`). No SETTING timer write, no IPQC
>   judgement write, no qty write, no PAUSE/RESUME, no signoff.
>
> When P10.7b–i ships the operator UI on top of this, every write
> path goes through a screen an operator can leave mid-shift. Without
> a single contract enumerating WHICH transitions are legal +
> serialised + auditable, two operators on two devices CAN drive the
> same WO into an inconsistent state (e.g. operator A on Pad-01 hits
> `SETTING_DONE` while operator B on Pad-02 hits `PREPRESS_NG` — both
> succeed, one stomps the other's write).
>
> **Audit cross-link.** This doc consolidates §B.8 row 3 ("Per-shift
> state machine corruption — HIGH"), §C-1 ("the legacy state machine
> is already shipped"), and §B.2 ("P10.7 re-frame: UI cost, not
> schema cost") of `AUDIT-3-CODEBASES-2026-06-04.md`.
>
> **Sources cited.** Every claim below is line-numbered against an
> absolute path so Henry can verify.

## 2. State inventory

### 2.1 The canonical set (locked)

The contract uses a **10-state canonical model** that is a strict
superset of the legacy 8-state and matches the SpecHub
`002_mes_scan_product.sql` enum **except** that two non-terminal
states from the SpecHub HTML prototype (`FQC_PENDING`, `OQC_PENDING`)
are added to model the late-flow QC gates that legacy already ships
as `ProcessStepCode.Fqc` and `ProcessStepCode.Oqc`. The
prototype-only `SHIPPED` is mapped onto `DONE` — there is no
operational difference shop-side once OQC passes.

Recommendation: **the database column** keeps the legacy
`ProcessStepCode` enum (8 values) for backward compatibility, and a
NEW additive column `MesPhase` carries the canonical 10-state. Both
columns are server-derived from each other at write time via a
deterministic projection in `WorkOrderStateMachine` (extended). This
keeps every existing Web Razor page working unchanged while giving
the Hybrid client the SpecHub-shaped flow it needs.

| # | Canonical name | Maps to legacy `ProcessStepCode` | Maps to legacy `WoStatus` | Terminal? |
| --- | --- | --- | --- | --- |
| 1 | `NEW` | `PrePressCheck` | `Draft` | No |
| 2 | `PREPRESS` | `PrePressCheck` | `InProgress` | No |
| 3 | `SETTING` | `OpSetting` | `InProgress` | No |
| 4 | `IPQC_WAIT` | `IpqcApproval` | `InProgress` | No |
| 5 | `IPQC_APPROVED` | `ReadyToRun` | `InProgress` | No |
| 6 | `QA_PENDING` | `IpqcApproval` (special-accept side-branch) | `OnHold` | No |
| 7 | `RUNNING` | `Running` | `InProgress` | No |
| 8 | `PAUSED` | `Running` | `OnHold` | No |
| 9 | `FQC_PENDING` | `Fqc` | `InProgress` | No |
| 10 | `OQC_PENDING` | `Oqc` | `InProgress` | No |
| 11 | `DONE` | `Closed` | `Closed` / `Finished` | Yes |
| 12 | `CANCELLED` | (new — not in legacy enum) | `Cancelled` | Yes |

Two terminal states total (`DONE`, `CANCELLED`). `STOPPED` from
SpecHub merges into `CANCELLED` (semantic match — operator-decided
non-completion). `SHIPPED` from prototype merges into `DONE`
(shipping is a post-MES Logistics event, out of scope for P10.7).

**Legacy compatibility constraint.** Existing CCL.MES.Web Razor pages
read `WorkOrder.CurrentStep` (the legacy enum). They MUST keep
working unchanged when the Hybrid client drives a new SETTING /
RUNNING / PAUSED transition. The `MesPhase` → `ProcessStepCode`
projection (server-side) ensures this:

| `MesPhase` | Projection to `ProcessStepCode` |
| --- | --- |
| `NEW` / `PREPRESS` | `PrePressCheck` |
| `SETTING` | `OpSetting` |
| `IPQC_WAIT` / `QA_PENDING` | `IpqcApproval` |
| `IPQC_APPROVED` | `ReadyToRun` |
| `RUNNING` / `PAUSED` | `Running` |
| `FQC_PENDING` | `Fqc` |
| `OQC_PENDING` | `Oqc` |
| `DONE` / `CANCELLED` | `Closed` |

This projection is deterministic, idempotent, and one-way (you
cannot recover `MesPhase` from `ProcessStepCode` alone for the
collapsed pairs — but the new column is the source of truth, so the
loss only matters for legacy reads). Legacy Razor pages keep their
8-step display because they read `ProcessStepCode`; the new shop-floor
UI reads `MesPhase`.

### 2.2 Per-state semantics

For each canonical state: WHO can enter it (the role at the moment
of the event firing the entry transition); WHO can exit it; what
child-table writes are valid in it; the timer / clock state the UI
should be displaying.

| State | Entry-by role | Exit-by role | Valid child writes | Timer / clock |
| --- | --- | --- | --- | --- |
| `NEW` | system (`/api/work-orders` POST) | scanner: any logged-in shop-floor role | none (master only) | none |
| `PREPRESS` | scanner of any role (`scan-wo` event) | OP role (`operator` / `production`) | `wo_materials` rows (one per BOM line) + `wo_plate_check` + `wo_cutter_check` | none |
| `SETTING` | OP role | OP role that ENTERED setting (4-eye lock) OR `admin` / `sys` | `wo_setting_log` (1:1) | running stopwatch from `setting_start_at` |
| `IPQC_WAIT` | OP role | IPQC sign-in (`qc` role via "Gọi IPQC" 4-eye modal) | none — checks rows guarded until IPQC signed in | idle |
| `QA_PENDING` | IPQC role (judgement = `SPECIAL_ACCEPT`) | QA Manager (`qc` + admin) | `ipqc_checks.qa_decision` only | running stopwatch since `ipqc_at` |
| `IPQC_APPROVED` | IPQC role (judgement = `GO_RUN`) OR QA (approve special) | OP role | `ipqc_checks` immutable once written | idle |
| `RUNNING` | OP role | OP that opened session OR `admin` | `run_sessions` (insert new) + `run_events` qty_add | running stopwatch + qty counter |
| `PAUSED` | OP role | OP that paused OR `admin` | `run_events` PAUSE + RESUME | paused stopwatch + reason banner |
| `FQC_PENDING` | OP role (run-finish event) | FQC inspector (`qc` 4-eye) | `qc_inspections` of type FQC | idle |
| `OQC_PENDING` | FQC role (pass) | OQC inspector + 3-signature gate | `qc_inspections` of type OQC | idle |
| `DONE` | OQC sign-out (pass) OR `admin` force-done | (terminal) | append-only `mes_audit_log` only | snapshot summary |
| `CANCELLED` | `admin` / `sys` only — explicit operator decision | (terminal) | append-only `mes_audit_log` only | snapshot summary |

**Terminal states must never become entry source.** Once a WO
reaches `DONE` or `CANCELLED`, no event can pull it back into an
active state. Reworks are explicitly handled by emitting a new WO
(`SPEC_REVISE` audit + new `wo_code`) rather than reviving a
terminal one. Rationale: it lets the OEE / yield aggregates stay
sane and lets `mes_audit_log` retention treat closed WOs as
archive candidates.

## 3. Transition matrix

### 3.1 The grid

FROM × TO grid. Each cell is one of {`allowed` / `blocked` /
`requires-condition` / `requires-signoff` / `recovery-only`}.

`allowed` = transition fires on the event, no extra check beyond
the event itself.
`requires-condition` = a domain predicate must hold (e.g. all PREPRESS
rows OK before SETTING can start).
`requires-signoff` = a separate role's credentials must be presented
in the same request (4-eye principle — IPQC / FQC / OQC).
`recovery-only` = transition is admin-only and emits a
`SYS_RECOVERY` audit row (§8).
`blocked` = no event can produce this transition.

## 4. Per-shift invariants

### 4.1 Shift boundaries do not interrupt WO state

The canonical model is **shift-agnostic at the WO level**. A WO that
is `SETTING` at 14:00 stays `SETTING` at 14:01 even if shift A ends
at 14:00 and shift B starts at 14:01. State transitions are
event-driven — they only fire when an operator acts. No transition
fires "automatically at shift boundary".

### 4.2 Operator handoff is explicit, not implicit

When operator A leaves mid-shift (e.g. ends shift in `SETTING`),
operator B picking up the WO at the same physical machine must:

1. Scan the WO QR to load it (event: `SCAN_WO` — emits a fresh
   audit row but does NOT change state, just `mes_audit_log` insert).
2. Authenticate at their own credentials (badge-tap or password).
3. EITHER continue the in-progress `wo_setting_log` (allowed because
   the 4-eye lock binds the `op_user_id` to the user who CREATED the
   log; operator B becomes the closer only if SETTING is the state
   and operator B passes the same machine-bind check) OR explicitly
   abort.

The 4-eye lock matters here. `wo_setting_log.op_user_id` is set on
SETTING entry. The `SETTING → IPQC_WAIT` transition (event
`SETTING_DONE`) checks `wo_setting_log.op_user_id == current_user_id`
OR `current_user_id IN (admin, sys)`. If B tries to close A's
setting, server returns 403 + audit row `WO_STATE_CONFLICT` with
detail `{ reason: "op_user_id_mismatch", expected, actual }`. UI
banner: "Setting was opened by <A>. Get A to close it, or escalate
to a supervisor."

### 4.3 The 3-5 cells most at risk of cross-shift corruption

| Cell | Corruption risk | Contract defence |
| --- | --- | --- |
| `SETTING → IPQC_WAIT` | B closes A's setting → false `wo_setting_log` shape (duration includes idle gap between shifts) | 4-eye op_user_id check; admin override emits explicit `WO_SETTING_ABORT` + reopen as new SETTING with B as op_user |
| `RUNNING → PAUSED` | B taps Pause on A's open `run_sessions` → `qty_good_delta` ambiguity | Pause event must reference current `run_session_id`; lock 4-eye on `run_sessions.op_user_id` for non-admin |
| `PAUSED → RUNNING` | B resumes a session A paused at end-of-shift → session timer span crosses shift boundary, OEE math wrong | Resume requires the SAME `op_user_id` as opened the session OR admin emits explicit `WO_RUN_PAUSE` + new `run_sessions` row with B as new owner |
| `QA_PENDING → IPQC_APPROVED` | QA Manager A starts review, QA Manager B approves on a different device — concurrent writes overwrite `qa_decision` | Optimistic concurrency token on `WorkOrder.RowVersion` (§6.1); whichever write lands second gets 409 + `WO_STATE_CONFLICT` audit |
| `RUNNING` qty increments | Two devices on the same WO (e.g. tablet + pendant scanner) increment `qty_good_delta` simultaneously — last write wins, qty under-counts | `run_events QTY_ADD` is **append-only** per `run_session_id`; the aggregate is computed by summing the events not by overwriting a counter |

The append-only / sum-aggregate pattern for qty (§4.3 row 5) is
specifically called out because the legacy `WorkOrder.ProducedQty`
int (`WorkOrder.cs:26`) IS overwriteable today and IS the
last-writer-wins risk. The contract replaces direct
`UpdateFlagsAsync({ProducedQty: N})` writes with `QTY_ADD` events in
`run_events`, and `WorkOrder.ProducedQty` becomes a server-derived
projection from `SUM(run_events.qty_good_delta)`. Legacy callers that
read `ProducedQty` keep working.

### 4.4 Shift-boundary audit emit

The MES audit logger SHOULD include a `shift_code` field in
`detail_json` for every state transition. Shift code is derived
server-side from the wall-clock + the shift master table (CCL
shifts: 06:00-14:00 / 14:00-22:00 / 22:00-06:00). This lets
forensic queries filter "all transitions in shift B 2026-06-15"
cheaply. NOT included in the canonical schema fields — it's a JSON
key inside the existing `detail` JSON column.

### 5.3 The BOM snapshot rule

`wo_materials` rows are created at WO creation time from a snapshot
of the BOM (`ManufacturingStructure`). They are NOT recomputed when
the source BOM revises post-WO-create. Rationale: production must be
able to complete a WO against the BOM that was valid when the
operator started — a mid-WO BOM revision (engineering change) does
not retroactively affect WIP. This matches the spec-revision-snapshot
pattern (`ProductRevisionId` on `WorkOrder.cs:18`).

## 6. Concurrency rules

### 6.1 Optimistic concurrency token

**Add `RowVersion`** (EF Core convention name) to `WorkOrder`:

```csharp
[Timestamp]
public byte[] RowVersion { get; set; } = Array.Empty<byte>();
```

EF Core handles the round-trip — every UPDATE includes
`WHERE Id = @id AND RowVersion = @originalRowVersion`. SQL Server
auto-bumps; SQLite needs a trigger (see §9 — out of scope for this
contract).

**API contract:** every mutation endpoint must accept the client's
last-known `RowVersion` via `If-Match` HTTP header (base64-encoded
byte array). Server:

1. If `If-Match` missing on a write → 428 Precondition Required.
2. If `If-Match` does not match current row → 409 Conflict + emit
   `WO_STATE_CONFLICT` audit row with detail JSON
   `{ wo_id, attempted_action, client_version, server_version }` (do
   NOT log the raw `RowVersion` bytes — log the base64 string).
3. On success → response `ETag` header carries the new `RowVersion`.

The client UI shows a banner: "Another operator just updated this
WO — please reload." After reload, the client retries with the
fresh version.

### 6.2 Idempotency-Key contract

Every mutation endpoint accepts `Idempotency-Key` header (UUID v4
generated client-side per intent). Server:

1. On request, hash the `(actor_id, endpoint_path, body_sha256)` and
   compare with the row in `idempotency_ledger` keyed by the header
   value.
2. If row exists with matching hash + within TTL → replay stored
   response (200 with original body).
3. If row exists with DIFFERENT hash → 422 + `idempotency_replay`
   audit row (operator is retrying with different inputs — UI bug).
4. If no row → process request, write result + hash to
   `idempotency_ledger`.

TTL is **out-of-scope** for this contract — recommend 24h to match
the Ops Control MES-2 convention (CLAUDE.md sprint MES-2 lineage),
but it's a per-PR knob.

### 6.3 What gets serialised vs concurrent

| Concurrent allowed | Serialised (DB-level lock) |
| --- | --- |
| `GET /wo/{id}` (drawer reads) | Any state-transition write — `RowVersion` enforces |
| `GET /wo/{id}/audit-log` | `wo_materials` rows (PK lock per `bom_line_idx`) |
| Multiple devices polling | `wo_setting_log` insert (1:1 PK is the lock) |
| Multiple inspectors viewing IPQC criteria | `run_events QTY_ADD` (NO lock needed — append-only insert into log; aggregate is sum) |

Two operators on the same WO at the same time: **reads are
concurrent, writes serialise via RowVersion**. The last-writer-wins
problem is replaced by first-writer-wins-loser-gets-409.

### 6.4 The qty-counter exception

`run_events QTY_ADD` (`002_mes_scan_product.sql:252-265`) is the
ONE write path that does NOT take a `RowVersion` check. Rationale:

- It's append-only; old rows are never re-read or mutated.
- Two operators adding `+5 good` simultaneously must produce
  `+10 good` net, not 409 one of them.
- The aggregate (`ProducedQty`) is a server-side sum, not a stored
  counter.

The `RowVersion` on `WorkOrder` does NOT bump on a `QTY_ADD` event
— it's a child-table append, not a parent-state mutation. State
transitions out of `RUNNING` (PAUSE / FINISH) DO bump `RowVersion`
and DO require `If-Match`.

This is the only carve-out. Every other write path is `RowVersion`-
gated.

### 7.3 Sensitive-field handling

The audit `detail` JSON is searchable + retained 90 days (Q13 in
plan §6.3, still open). What CAN go in:

- Quantities, codes, timestamps, FK values.
- User IDs (long) and usernames (string from
  `AuditLog.ActorUsername`).
- IP addresses (already captured at the row level —
  `AuditLog.IpAddress`).
- Free-text REASON fields (e.g. `special_accept_reason`,
  pause `note`). Length-limited to ≤ 500 chars; server enforces
  truncation.

What MUST NOT go in (sanitize whitelist enforced server-side, same
as legacy convention `AuditLog.cs:34-40`):

- Passwords, hashes, tokens, session cookies.
- Signature image bytes (the SIGNATURE goes to a separate
  `signatures` table referenced by ID; the audit detail carries only
  the signature row PK, never the bytes).
- Customer PII beyond what's already in `WorkOrder` (customer name
  is fine — it's on the master row).

### 7.4 Append-only enforcement

`mes_audit_log` (or whatever the table name lands as — recommend
re-using existing `AuditLog` table since the row shape fits — see
§5.1) MUST have UPDATE + DELETE revoked at DB-role level for the
app's runtime role. The plpgsql REVOKE block in
`002_mes_scan_product.sql:309-315` is the template; the equivalent
for SQLite is to NOT grant UPDATE/DELETE via the connection's
prepared statement set (enforce at code-review time via grep audit).

## 8. Recovery paths

### 8.1 "WO stuck in state X — admin force-unstick"

When a WO is wedged (e.g. operator left mid-SETTING, never logged
back, no admin available):

```bash
# 1. SSH to the Hybrid API host.
ssh admin@<host>

# 2. Identify the wedged WO.
sqlite3 /opt/ccl-mes-hybrid/data/mes.db \
  "SELECT Id, WoNo, CurrentStep, UpdatedAt FROM WorkOrders WHERE WoNo = 'WO-26-XXXX';"

# 3. Use the admin recovery endpoint (P10.7a ships this).
curl -X POST https://<host>/api/v1/work-orders/{id}/admin-force-phase \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{"target_phase": "PREPRESS", "reason": "operator A left mid-shift, B picking up"}'
```

The endpoint:
1. Requires `sys` role (NOT `admin` — even stricter).
2. Emits `SYS_RECOVERY` audit row with `from_phase`, `to_phase`,
   `reason`, the sys-user's ID.
3. Bumps `WorkOrder.RowVersion`.
4. Does NOT delete or modify child-table rows (the operator who
   resumes must explicitly re-open them).

> **§8.1 amendment — P10.7a-2.2 (2026-06-05).** §2.2 says CANCELLED
> entry is "admin / sys only" while §8.1 step 1 above says the
> endpoint "Requires `sys` role". These were inconsistent. The
> shipped policy reconciles both:
>
> | Reading | What it means | Where it's enforced |
> | --- | --- | --- |
> | §2.2 "admin / sys" | Who CAN call the endpoint | `[Authorize(Policy = "AdminOnly")]` on the controller — admin users hit the wire path. |
> | §8.1 "sys role" | Who APPEARS in audit attribution | The seeded `sys-recovery` user (Role=`Sys`, `IsActive=false`) is referenced via `detail.sys_user_id` on every `SYS_RECOVERY` row. No live human has Role=`Sys`. |
>
> The live admin's username lands in `ActorUsername`. `detail.sys_user_id`
> labels the act as a system-recovery event for the audit reader. Both
> §-sections are satisfied without making the seeded sys account
> loginable.
>
> **Child-rows preservation (point 4) — clarifying note.** "Does NOT
> delete or modify child-table rows" means future-aggregation queries
> (yield / OEE / scrap-rate) MUST filter out CANCELLED WOs at SELECT

>
> **Request body (Henry-confirmed Q2 — structured).** Body is

>   `force.invalid_reason_code`.
> - `ReasonNote` is free-text, 1-500 chars.
>
> `detail.reason` on the audit row is `{ "code": "...", "note": "..." }`.
>
> **Forceable cells (Henry-confirmed FROM×TO).** Exactly 11 cells per

### 8.1-backlog — extending backward force beyond SETTING → PREPRESS

P10.7a-2.2's §8.1 amendment freezes the forceable matrix at the 11
cells §3.1 enumerates today: SETTING → PREPRESS + 10× *→CANCELLED.
Operationally this means any wedge OUTSIDE of SETTING (e.g. operator
stuck at IPQC_WAIT with no IPQC available, FQC inspector left
mid-shift) has only "wait OR force-cancel" as recovery options.

If post-go-live operational data shows admins need additional
backward force paths (e.g. IPQC_WAIT → PREPRESS to redo setup,
FQC_PENDING → PREPRESS for a full rerun without re-issuing a WO),
file the request as a contract amendment to §3.1 + this section.
Do NOT smuggle additional cells in via the endpoint — the matrix
test (`WorkOrderStateMachineIsForceableTests`) locks the contract
against drift; any new cell must land via an explicit §3.1 amendment
that fans out through the predicate + tests + audit emit table.

### 8.2 "Production count diverged from physical reality"

The `run_events QTY_ADD` log is append-only and time-stamped per
event. A divergence between `WorkOrder.ProducedQty` (server-derived
sum) and physical count means one of:

1. An operator typed wrong qty (real-world miscount).
2. Two devices double-incremented the same physical batch.

Recovery procedure:

```bash
# 1. Replay the audit trail to see who added what when.
curl https://<host>/api/v1/work-orders/{id}/qty-events \
  -H "Authorization: Bearer $QC_TOKEN"

# Output: ordered list of QTY_ADD events with actor + machine + delta.

# 2. If a specific event needs correcting, insert a COMPENSATING event
#    (never DELETE — append-only):
curl -X POST https://<host>/api/v1/work-orders/{id}/qty-adjust \
  -d '{"qty_good_delta": -5, "qty_ng_delta": 0, "reason_code": "QTY_CORRECTION", "note": "double-counted batch 14, physical recount = 95"}'
```

`QTY_CORRECTION` lives in `downtime_reasons` as a special
non-downtime code (`category = 'Other'`); rows it emits are flagged
in OEE math so they don't affect availability %.

### 8.3 "Concurrent-edit storm during operator handoff"

If `WO_STATE_CONFLICT` audit rows spike on a single WO (>3 in 60
seconds), the UI is stuck in a retry loop:

1. Force-revoke all active sessions for that WO via the existing
   session-revoke endpoint (already in legacy
   `PG_CHANGE_REVOKE` pattern).
2. The next scan of the WO QR creates fresh sessions, breaking the
   loop.

This is documented per P10.7a sub-task — server emits a metric
counter on each `WO_STATE_CONFLICT` and alerts on the threshold.

### 8.4 Backup + audit-trail forensic replay

A nightly snapshot of `mes_audit_log` (or the merged `AuditLogs`
table) is required before P10.7a opens. The retention window
question (Q13 plan §6.3) is still OPEN — recommend 90 days hot
storage + indefinite cold archive in
`/opt/ccl-mes-hybrid/audit-archive/<YYYY>/<MM>/`. Audit log
archival job runs at 02:00 daily.

Forensic replay of a single WO:

```bash
sqlite3 /opt/ccl-mes-hybrid/data/mes.db \
  "SELECT Timestamp, Action, Detail FROM AuditLogs
   WHERE TargetType = 'WorkOrder' AND TargetId = '<id>'
   ORDER BY Timestamp ASC;"
```

This MUST reconstruct the exact phase + child-table sequence the
operators went through. If a row is missing, the audit emit point
was bypassed (P10.7a must include a grep test that every
state-machine transition has an `_audit.EmitAsync` call within the
same DB transaction).
