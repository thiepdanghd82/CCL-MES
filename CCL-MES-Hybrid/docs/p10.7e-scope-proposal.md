## Scope at a glance

review gates after RUNNING finishes and before the WO ships out the
factory. Today's 7d stack lands DONE as the terminal phase from the
operator's perspective; FQC_PENDING + OQC_PENDING are deferred
placeholder cards in `RunningDashboard.DeferredPhaseInfo`. 7e
replaces those placeholders with real dashboards + adds the
**SHIPPED** terminal state to close the SpecHub quality loop.

| `RUNNING\|PAUSED → FQC_PENDING` | OP via `/run/finish` | ✓ (7c-2) | (unchanged) |
| `FQC_PENDING → OQC_PENDING` | QC via FQC judgment "Pass" | placeholder card only | **wire** |
| `FQC_PENDING → PREPRESS` (rework) | QC via FQC judgment "Reject" | n/a | **wire** |

## Q1 — Add `SHIPPED` to MesPhase enum, or repurpose `DONE`?

**Context**: SpecHub Phase 2 plan ends with `SHIPPED`; `DONE` is
relegated to "Production Done" (transient post-RUNNING, pre-FQC).
Our current `MesPhase` enum has `DONE` as terminal; nothing past it.

**SpecHub citation**: `MES_QUALITY_REDESIGN_PLAN.md:43-48` + 54-59
explicitly enumerates 6 NEW state colors/icons including SHIPPED as
the closed.done final state.

**Recommended**: **YES, add `SHIPPED`** as a new MesPhase + migrate
to `DONE` being the post-RUNNING-pre-FQC transient (one-tick auto
to FQC_PENDING). Server-side state-machine §3 grid gains 4 new cells:

- `RUNNING|PAUSED → DONE` (operator Finish — unchanged from 7c
  semantically but the next phase changes)
- `DONE → FQC_PENDING` (auto on Finish, single transaction)
- `OQC_PENDING → SHIPPED` (QC Pass with 3-sig)
- `SHIPPED → [*]` (terminal — no further transitions)

**Trade-off**:
- (+) Aligns with SpecHub quality-cycle convention used by ops floor.
- (+) Legacy DONE rows in prod DB stay valid; new flow uses SHIPPED.
- (−) +1 MesPhase enum value forces a state-machine §3.1 grid extension
  (144 → 156 cells). Theory tests update.
- (−) Existing `DeferredPhaseInfo` map entries for DONE/CANCELLED stay,
  + SHIPPED needs its own (read-only terminal placeholder until 7f
  ships the report dashboard).

**Contract gap**: SpecHub model also adds transient FQC_REJECT +
OQC_REJECT visual states (color/icon for the operator briefly seeing
"Rejected" before WO moves on). See Q2.

## Q2 — Persist FQC_REJECT + OQC_REJECT as MesPhase values, or emit-and-transition (no durable state)?

**Context**: SpecHub plan §Phase 2 lists FQC_REJECT + OQC_REJECT as
"transient" states. Question is whether they get a durable
MesPhase row.

**SpecHub citation**: `MES_QUALITY_REDESIGN_PLAN.md:56-58` —
explicitly tagged `// transient` in the WO_STATES const.

**Recommended**: **NO new MesPhase values** — emit dedicated audit
codes + transition in the same SaveChanges block:

- FQC judgment Reject → emit `WO_FQC_REJECT_TO_PREPRESS` audit +
  MesPhase = PREPRESS in one atomic write.
- OQC judgment Reject → emit `WO_OQC_REJECT_TO_FQC_PENDING` audit +
  MesPhase = FQC_PENDING in one atomic write.

Operator briefly sees a "Reject" toast in the dashboard then auto-
re-route (L21 OnPhaseChanged bubble fires) to the new phase's
dashboard — no separate "Reject placeholder" needed.

**Trade-off**:
- (+) Smaller enum, smaller state-machine grid, fewer DeferredPhaseInfo
  entries.
- (+) Audit-log timeline still captures the reject event for
  reporting / forensic trace.
- (−) Operator visual feedback ~200ms shorter than SpecHub's plan
  envisioned. Mitigation: render a green/red 2-second toast above
  the new dashboard naming the prior reject.
- (−) Loss of "currently rejected" filter by MesPhase index. Mitigation:
  filter via audit log timeline (which is the right place anyway —
  reject is a historic event, not a current state).

**Contract gap**: SpecHub does not specify whether the operator who
sees the post-reject phase needs to confirm awareness of WHY. Defer
to UX call in 7e-3.

## Q3 — Profile-driven item definitions for FQC + OQC: data table OR hardcoded slots like 7d IPQC?

**Context**: 7d IPQC has 4 hardcoded slots (Material/PrintA/PrintB/PrintC).
SpecHub has 12-item MES_FQC_PROFILE + 28-item MES_OQC_PROFILE +
acknowledges "Phase 1.5" plans to migrate IPQC itself to profile-driven.

**SpecHub citation**:
- `MES_QUALITY_REDESIGN_PLAN.md:23-24` — profiles defined as JS
  constants in their prototype, ready for backend wiring.
- §Phase 1 deferred to "Phase 1.5" the IPQC item-list refactor:
  "Refactor the 4 hard-coded OK/NG rows (material_status /
  print_a / print_b / print_c) into a render loop driven by
  `profile.sections[*].items`. Migrate `wo.ipqc` state from 4
  fixed fields → `wo.ipqc.checks: { [itemKey]: 'OK'|'NG' }` map."

**Recommended**: **Ship FQC + OQC as DATA-DRIVEN from day 1** —
do NOT repeat the IPQC hardcoded mistake. Schema:

```sql
-- New 7e tables
CREATE TABLE WoQcChecks (
    Id INTEGER PRIMARY KEY,
    WorkOrderId INTEGER NOT NULL,
    QcKind TEXT NOT NULL,            -- 'FQC' | 'OQC'
    ProfileSnapshotJson TEXT NOT NULL,   -- frozen copy of profile at start time
    Judgment TEXT NULL,              -- 'Pass' | 'Reject' | null while in-progress
    SubmittedBy TEXT NULL,
    SubmittedAt DATETIME NULL,
    -- 3-sig fields ONLY when QcKind='OQC' — see Q5
    ReviewedBy TEXT NULL,
    ReviewedAt DATETIME NULL,
    ApprovedBy TEXT NULL,
    ApprovedAt DATETIME NULL,
    UNIQUE(WorkOrderId, QcKind)      -- 1 active row per kind per WO
);

CREATE TABLE WoQcCheckItems (
    Id INTEGER PRIMARY KEY,
    WoQcCheckId INTEGER NOT NULL,
    ItemKey TEXT NOT NULL,           -- from profile.sections[*].items[*].key
    Status TEXT NOT NULL,            -- 'Pending' | 'Ok' | 'Ng'
    NgReasonCode TEXT NULL,
    NgNote TEXT NULL,
    PhotoBlobId INTEGER NULL,        -- see Q6
    UNIQUE(WoQcCheckId, ItemKey)
);
```

Server returns a flattened render-ready view that the dashboard
loops over. Profile changes apply to NEW WOs only — frozen snapshot
on existing rows preserves audit integrity.

**Trade-off**:
- (+) Future-proof: a 7f admin can edit profiles without touching
  schema or code. Per-product threshold (Q4) plugs in naturally.
- (+) Mirrors the SpecHub prototype shape; easy to compare.
- (+) Bonus IPQC refactor opportunity — SAME schema accepts QcKind='IPQC'.
  Defer the migration to 7f to keep 7d frozen for compliance.
- (−) ~2× implementation effort vs 4 hardcoded slots. Estimated
  10-12 hours dev + 8 hours test belt vs 5+4 for hardcoded.
- (−) Bunit dashboard tests need profile-fixture builders; can't
  hard-code 4 slot test-ids.

**Contract gap**: SpecHub defines the FQC + OQC profiles but does
NOT yet ship the profile-management UI. Defer to 7g.

## Q4 — Per-product QC threshold override: profile-level constants only, OR `Product.QcProfileOverride` JSON?

**Context**: Henry's hardware brief mentioned "per-product qc
threshold". SpecHub Phase 1 ships 5 process-typed profiles (Silk 20
items, Flexo 28, Indigo 24, CNC Press 17, RDC 13). What about
product-specific overrides (e.g. customer X needs ΔE ≤ 1, default
is ≤ 2)?

**SpecHub citation**: `MES_QUALITY_REDESIGN_PLAN.md` does NOT
explicitly address per-product overrides — Phase 1 ships process-
typed profiles only.

**Recommended**: **ADD `Product.QcProfileOverride` JSON field** —
optional per-item threshold overrides + per-item enable/disable.
Resolution chain on `GET /work-orders/{id}/qc/fqc`:

```
1. Product.QcProfileOverride[itemKey].threshold     (if set + non-null)
2. ProcessProfile[itemKey].threshold                (default per process)
3. ItemDefinition.threshold                         (hardcoded fallback)
```

Override UI: admin-only on Product edit screen. Defer the UI to a
follow-up PR (7e-5 or 7f); 7e ships the resolution logic + a
seed-script path for ops to populate via SQL until UI lands.

**Trade-off**:
- (+) Customer-specific compliance (X demands tighter ΔE) without
  touching the global profile.
- (+) Single resolution chain — debuggable + auditable.
- (−) JSON validation needed (Profile knows its item keys; override
  must whitelist against them).
- (−) Admin UI deferral means SQL seed path is the only edit
  surface in 7e. Acceptable for v1 since CCL Vietnam has ~10
  customer-specific overrides total.

**Contract gap**: SpecHub doesn't say what should happen if a
Product.QcProfileOverride references an item key NOT in the current
ProcessProfile. Recommended: log + ignore (the override is for the
intended product type only — silent ignore prevents stale config from
crashing FQC).

## Q5 — OQC 3-signature requirement (from CCL-10-F6): mirror Q3 dual-sig pattern, or simpler 1-sign?

**Context**: SpecHub plan §Phase 2 + the physical form CCL-10-F6
mandate 3 signatures on outgoing inspection: Inspector + Reviewer
+ Approver. Q3 7d dual-sig (IPQC submitter ≠ QA approver) is the
prior art.

**SpecHub citation**: `MES_QUALITY_REDESIGN_PLAN.md:24` — "28 items
including RoHS heavy metals + 3 signatures from CCL-10-F6".

**Recommended**: **Generalise the Q3 pattern — multi-sig with explicit
distinct-user invariants**:

- Inspector field — pre-populated to the QC operator who started
  the OQC check.
- Reviewer field — DIFFERENT person taps "Review" → server checks
  `ReviewedBy != InspectedBy`.
- Approver field — DIFFERENT person again taps "Approve" → server
  checks `ApprovedBy != ReviewedBy AND ApprovedBy != InspectedBy`.

Implementation reuses the 7d `IpqcDualSigOptions` shape — rename
to `WoQcSigPolicyOptions` with 3 toggles
(`OqcRequireDistinctReviewer` / `OqcRequireDistinctApprover` /
`OqcRequireApproverDistinctFromInspector`), all default-ON per
Lesson L20 (typo-safe whitelist parse + boot probe).

Error codes mirror Q3:
- `oqc.same_user_as_inspector` (Reviewer == Inspector)
- `oqc.same_user_as_inspector_or_reviewer` (Approver == one of the
  earlier two)
- `WO_OQC_REVIEW_DENIED` + `WO_OQC_APPROVE_DENIED` audit codes.

UI: 3 inline sign cards (Inspector pre-stamped; Reviewer + Approver
gated by distinct-user client guard mirroring `Q3SameUserBanner`
pattern).

**Trade-off**:
- (+) Compliance-aligned (matches the physical signature card).
- (+) Reuses the L20 default-ON flag pattern + the Q3 client guard
  pattern verbatim — proven scaffolding.
- (−) 3 sign cards = 3 sequential UI interactions. Slower than the
  current QA "Approve" tap. Acceptable: OQC happens once per WO,
  not 1000 times.
- (−) 3 env flags increase deploy-time configuration surface.
  Mitigation: bundle as a single `OPS_OQC_REQUIRE_MULTI_SIG`
  master flag that defaults all 3 to ON.

**Contract gap**: SpecHub doesn't specify HOW the 3 signatures are
ordered. Recommended: strict Inspector → Reviewer → Approver
sequence (server-side state machine refuses out-of-order taps with
a `oqc.signature_out_of_order` 422).

## Q6 — Photo evidence attachment on NG: blob storage now, or defer to 7f?

**Context**: Henry's hardware brief mentioned "photo evidence";
SpecHub also lists "optional photo upload" for NG cases at
`06-mes-scan-product.md:101`.

**SpecHub citation**: `06-mes-scan-product.md:101` —
> "NG → mở modal nhập `ng_reason_code` từ master `ng_reasons.MATERIAL`
>  + free text `note` + optional photo upload"

**Recommended**: **ADD `WoQcPhoto` table + IBlobStore wiring in
7e-1** but keep upload OPTIONAL for IPQC (don't break 7d contract)
and ENCOURAGED for FQC/OQC NG (warehouse traceability). Storage:
reuse the existing `IBlobStore` (filesystem under
`<DataDir>/blobs/wo-qc-photos/<wo_id>/<check_id>/<uuid>.{jpg,png}`).
Server enforces:

- Max 5 MB per photo
- Allowed MIME: `image/jpeg` + `image/png` only
- Max 4 photos per check item
- Streamed multipart upload (no full-file buffer, see Lesson D-5b)

Endpoint shape:
- `POST /work-orders/{id}/qc/{kind}/items/{itemKey}/photos` — upload
- `GET /work-orders/{id}/qc/{kind}/items/{itemKey}/photos/{photoId}` — download
- `DELETE /work-orders/{id}/qc/{kind}/items/{itemKey}/photos/{photoId}` — remove

Audit: every upload + delete emits `WO_QC_PHOTO_ADD` / `WO_QC_PHOTO_DELETE`
with size + sha256.

**Trade-off**:
- (+) Closes the SpecHub-spec gap from day 1; warehouse audit ready.
- (+) Reuses 7e's existing IBlobStore (already wired for Drawings).
- (+) Streaming upload reuses the Drawings 6-guard pattern (Lesson D-5b).
- (−) Catalyst-side camera capture is non-trivial (MAUI Camera API).
  Mitigation: ship file-picker first (upload from saved photo), camera
  in 7f.
- (−) Blob size accumulates fast: ~1 MB per photo × 4 per item × 12 FQC items
  = ~48 MB per WO theoretical max. Mitigation: nightly cleanup script
  archiving photos for WOs > 90 days old.

**Contract gap**: SpecHub doesn't specify retention policy. Recommended:
keep photos forever (audit compliance) unless ops requests otherwise.

**Context**: 7d added 4 audit codes (`WO_IPQC_CHECK` /
`WO_IPQC_JUDGMENT` / `WO_QA_APPROVE` / `WO_QA_APPROVE_DENIED`). 7e
needs equivalents for FQC + OQC + transitions.

**SpecHub citation**: `06-mes-scan-product.md:254` lists the

(stops at `RUN_FINISH`). 7e is greenfield on naming.

**Recommended**: **Mirror 7d naming verbatim** — 12 new codes:

- `WO_FQC_CHECK_ITEM` — single FQC item set (Ok/Ng)
- `WO_FQC_JUDGMENT` — Pass/Reject decision
- `WO_FQC_REJECT_TO_PREPRESS` — Reject → PREPRESS transition (Q2)
- `WO_OQC_CHECK_ITEM` — single OQC item set
- `WO_OQC_INSPECT` — Inspector signs
- `WO_OQC_REVIEW` — Reviewer signs
- `WO_OQC_APPROVE` — Approver signs (terminal sign)
- `WO_OQC_REVIEW_DENIED` — Q5 dual-sig violation on Review (same as Inspector)
- `WO_OQC_APPROVE_DENIED` — Q5 dual-sig violation on Approve
- `WO_OQC_REJECT_TO_FQC_PENDING` — Reject → FQC_PENDING (Q2)
- `WO_SHIPPED` — terminal SHIPPED transition (Q1)
- `WO_QC_PHOTO_ADD` + `WO_QC_PHOTO_DELETE` — photo lifecycle (Q6)

Rollup helpers mirror 7d shape — `FqcReadinessRollup.Compute` + 
`OqcReadinessRollup.Compute` pure helpers with `IsReadyForJudgment`
+ `AllOk` + `AnyNg` + `IsJudgmentConsistent`.

**Trade-off**:
- (+) Operator + auditor pattern-recognition: 7d→7e same shape.
- (+) Greppable in 1 line per pattern.
- (−) 12 new codes is a lot for one phase. Mitigation: 7e ships them
  ALL in 7e-1 domain (no rolling additions across 7e-2/3/4).

**Contract gap**: none — fully under our control.

## Q8 — Reports: ship minimal /work-orders/{id}/summary in 7e, or defer to 7f?

**Context**: SpecHub §Phase 6 (`06-mes-scan-product.md:182-187`)
specifies the DONE-phase summary content:

> Final summary:
> - TOTAL OUTPUT / GOOD / REJECT
> - TOTAL RUNTIME (sum sessions duration)
> - PAUSE EVENTS count + breakdown by reason (Pareto)
> WO ở DONE chỉ read-only — không update qty được nữa.

Plus the KPI formulae at `06-mes-scan-product.md:174-178`:

> - `availability = (run_time) / (run_time + pause_time)` per session
> - `performance = qty_done / (planned_speed × run_time)`
> - `quality = (qty_done - qty_ng) / qty_done`
> - `OEE = availability × performance × quality`

**Recommended**: **SHIP minimal JSON report in 7e-3** —
`GET /work-orders/{id}/summary` returning a SINGLE flat JSON with:

```json
{
  "wo": { "no": "WO-26-XXXX", "shipped_at": "..." },
  "totals": { "qty_target": N, "qty_done": N, "qty_ng": N },
  "runtime": { "run_seconds": N, "pause_seconds": N, "session_count": N },
  "oee": { "availability": 0.92, "performance": 0.85, "quality": 0.97, "oee": 0.76 },
  "pause_pareto": [
    { "reason_code": "MAINT", "count": 3, "total_seconds": 1200 },
    ...
  ],
  "qc_summary": {
    "ipqc": { "judgment": "GoRun", "submitted_by": "...", "qa_approver": null },
    "fqc":  { "judgment": "Pass",  "submitted_by": "..." },
    "oqc":  { "judgment": "Pass",  "inspector": "...", "reviewer": "...", "approver": "..." }
  }
}
```

UI: SHIPPED dashboard renders this summary as a read-only card.
Export to xlsx (matching CCL-10-F6 form layout) deferred to 7f
(needs ExcelJS-equivalent for .NET; OpenXmlPackage candidate).

**Trade-off**:
- (+) Closes the SpecHub spec gap for the DONE/SHIPPED phase
  immediately — operators see the full summary card on first ship.
- (+) JSON is reusable for any future export pipeline (xlsx / PDF /
  email / ERP push).
- (−) OEE calculation has 1 data point we don't track yet:
  `planned_speed` (units/hr per machine). Mitigation: fetch from
  `MachineProfiles.PlannedUnitsPerHour` if available; emit
  `performance=null` + UI shows "—" when missing.
- (−) Pareto chart deferred — UI ships a simple table. Charting is
  7f scope.

**Contract gap**: SpecHub silent on whether the summary should be
"live" (recompute on every GET) or "frozen" (snapshot at SHIPPED
time). Recommended: live recompute — gives correct picture even when
late corrections are entered via `/run/qty/correct` between Finish
and Ship.
