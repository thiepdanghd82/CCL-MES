## 2. SpecHub canonical contract (source of truth for 7c)

Per `SpecHub/docs/06-mes-scan-product.md` § "State machine" + § "5-phase flow detail":

```
PREPRESS  ✅ shipped 7b
   ↓
SETTING       Phase 2 — live timer + 6-item ref checklist + OP-only exit
   ↓
IPQC_WAIT     Phase 3 — notify QC, 4 checks (Material + 3 Print) + judgment
   ↓
IPQC_APPROVED Phase 4 — confirmation gate (tick + Start Run)
   ↓
RUNNING ⇄ PAUSED    Phase 5 — counter capture + pause reasons + finish
   ↓
DONE          Phase 6 — final summary, read-only
```

SpecHub's 5-phase ↔ CCL-MES §3.1 12-state mapping:

| SpecHub | CCL-MES `MesPhase` | Notes |
| --- | --- | --- |
| PREPRESS | `PREPRESS` | 7b closed |
| SETTING | `SETTING` + `SETTING_DONE` | CCL-MES splits "in setup" vs "setup-done-awaiting-IPQC" |
| IPQC_WAIT | `IPQC_WAIT` | matches |
| IPQC_APPROVED | `IPQC_PASS` | matches |
| RUNNING | `RUNNING` | matches |
| PAUSED | `PAUSED` | matches |
| QA_PENDING | (deferred — out of 7c scope) | rare workflow; defer to 7d |
| DONE | `FQC_PENDING` → `FQC_PASS` → `CLOSED` | CCL-MES gates DONE through FQC; that's 7d |

## 3. 7c proposed scope — SETTING + RUNNING + PAUSED

7c covers operator-driven Setting → Running → Paused. **IPQC + QA_PENDING + FQC stay in 7d** (separate role gate — QC/QA vs OP).

### 3.1 SETTING surface (Phase 2)

- **Entry**: WO at `MesPhase=SETTING` after PREPRESS Advance. Server already transitions on the 7b Advance button.
- **UI**: new `SettingDashboard.razor` inside `WorkOrders.razor` (dispatch when `IsSettingStep(currentStep)`). Layout:
  - Big **live timer** since `WorkOrder.SettingStartAt` (server-stamped on transition into SETTING).
  - 6-item **ref checklist** — read-only ticks (operator self-tick, no server enforcement; informational only per SpecHub spec).
  - **"Setting Done"** button (single primary CTA, OP role only).
- **Endpoint**: `POST /api/v2/work-orders/{id}/setting/done` with If-Match + Idempotency-Key (same 7a-1.3 envelope). Server-side:
  - Validates `MesPhase == SETTING`.
  - Stamps `WorkOrder.SettingEndAt` + computes `SettingDurationSec`.
  - Transitions `SETTING → SETTING_DONE` (or directly to `IPQC_WAIT` per contract decision below).
  - Audit event `WO_SETTING_DONE` with `setting_duration_sec` in detail JSON.
- **Open question for Henry**: split `SETTING_DONE` (intermediate state, OP done but IPQC not yet) vs. direct `SETTING → IPQC_WAIT`? Contract §3.1 has both; SpecHub collapses to `IPQC_WAIT` immediately. Recommendation: follow SpecHub — direct transition — unless your factory operationally needs the split.

### 3.2 RUNNING surface (Phase 5)

- **Entry**: WO at `MesPhase=RUNNING` after IPQC_PASS (7d scope) flips it. For 7c we assume IPQC_PASS is reachable via the existing admin force-phase endpoint (operator-blocked path) until 7d ships the IPQC surface.
- **UI**: new `RunningDashboard.razor`:
  - **Big counter** `qty_done / qty_target` + progress bar. Live-updated by operator taps.
  - **+100 / +500 / +1000 / custom** quick-add buttons for `qty_done`.
  - **+5 / +10 / +20 NG** buttons for `qty_ng` + reason picker (Scrap kind, **reuse 7b-3's picker** + `<select>` + submit-gate).
  - **Pause** button → modal:
    - Reason dropdown populated from `GET /api/v2/reason-codes?kind=Pause` (the existing endpoint shipped in 7b-3; only `kind=Scrap` is currently consumed — `kind=Pause` is already supported, no server change needed).
    - Note input (optional 1-500 chars).
    - Submit: server transitions `RUNNING → PAUSED` + creates `WoPauseEvent { wo_id, started_at, reason_code, note, started_by }`.
  - **Finish** button → confirm dialog → transitions to `FQC_PENDING` (handoff to 7d).
- **PAUSED state**:
  - Counter buttons disabled.
  - Big badge "PAUSED · <reason VN label> · ago N min".
  - **Resume** button → transitions `PAUSED → RUNNING` + stamps `WoPauseEvent.ended_at`.
  - **Finish** still available (force-close from PAUSED → `FQC_PENDING`).
- **Endpoints** (all follow 7a-1.3 envelope):
  - `POST /api/v2/work-orders/{id}/run/start` (idempotent via Idempotency-Key; the FIRST tap creates run session, subsequent taps are 200 replay).
  - `POST /api/v2/work-orders/{id}/run/qty` body `{ qty_done?: int, qty_ng?: int, ng_reason_code?: string, ng_note?: string }` — incremental add. **Both qty_done AND qty_ng are additive deltas, not absolute totals.** Server-side validation:
    - `qty_done < 0` → 422 `qty.invalid_delta`.
    - `qty_ng > 0` requires valid `ng_reason_code` ∈ Scrap catalog + `ng_note` (1-500 chars). Mirror of 7b-3 validation; reuses `prepress.invalid_reason_code` / `prepress.invalid_ng_note` shape — proposal: NEW codes `run.invalid_reason_code` / `run.invalid_ng_note` to distinguish.
  - `POST /api/v2/work-orders/{id}/run/pause` body `{ reason_code, note? }`.
  - `POST /api/v2/work-orders/{id}/run/resume` (no body).
  - `POST /api/v2/work-orders/{id}/run/finish` (no body, transitions to FQC_PENDING).
- **Audit events**: `WO_RUN_START`, `WO_RUN_QTY_ADD` (carries qty_done_delta + qty_ng_delta + ng_reason_code + ng_note), `WO_RUN_PAUSE`, `WO_RUN_RESUME`, `WO_RUN_FINISH`.

### 3.3 Domain additions

- New entity `WoRunSession { Id, WoId, StartedAt, EndedAt?, StartedBy, EndedBy?, RowVersion }` — one per RUNNING segment (a Pause/Resume creates a new row).
- New entity `WoPauseEvent { Id, WoId, RunSessionId?, StartedAt, EndedAt?, ReasonCode, Note?, StartedBy }` — links to the session it interrupted; null `EndedAt` while PAUSED.
- New entity `WoQtyEntry { Id, WoId, RunSessionId, Ts, QtyDoneDelta, QtyNgDelta, NgReasonCode?, NgNote?, EnteredBy }` — append-only ledger; current totals derived by `SUM(QtyDoneDelta)` / `SUM(QtyNgDelta)` per WO. Reject as a row instead of overwriting `WorkOrder.QtyDone` so the audit trail survives.
- WO row gains 3 fields: `SettingStartAt`, `SettingEndAt`, `SettingDurationSec` (computed at transition). Counter totals (`QtyDoneCached`, `QtyNgCached`) are denormalized snapshots updated on every `WO_RUN_QTY_ADD` — bench-marking shows aggregation across 50 ledger rows is sub-millisecond on SQLite so cache is opportunistic.
- New migration `20260607XXXXXX_AddRunningSurface` adds 3 tables + 3 WO columns + 3 indices.
- `WorkOrderStateMachine` extends with `RUNNING → PAUSED` + `PAUSED → RUNNING` + `* → FQC_PENDING (via Finish)` transitions.

### 3.4 Picker reuse (no new server work)

- The 7b-3 `GET /api/v2/reason-codes?kind=Scrap` endpoint already supports `kind=Pause`. The pause modal calls it with `kind=Pause` — 8 ML-* codes already seeded. **Zero new server endpoint** for the pause picker.
- The NG qty picker reuses `kind=Scrap` directly — 8 SC-* codes including the 4 PREPRESS-specific ones.

### Q1 — SETTING → IPQC_WAIT transition: direct or via intermediate `SETTING_DONE`?

| | |
| --- | --- |
| **Recommendation** | **Direct** — `SETTING` → `IPQC_WAIT` on Setting Done button tap. No intermediate `SETTING_DONE` state. |
| **SpecHub citation** | `docs/06-mes-scan-product.md` line 26 + 78: state diagram shows `SETTING --> IPQC_WAIT: setting done` with no intermediate state. Line 118: "Bấm OP Setting Done → POST /wo/:id/setting/done → ghi `setting.end_at` → status → `IPQC_WAIT` → broadcast WebSocket `wo_setting_done` event". The endpoint emits the event AND transitions phase atomically. |
| **Trade-off** | **Direct** (recommended): smaller state machine (12-state stays 12; no expansion to 13), simpler dashboard dispatch (`SETTING` UI vs `IPQC_WAIT` UI is the role gate operator can see), matches SpecHub semantics. **Intermediate `SETTING_DONE`** (alternative): would let CCL track "OP is done but QC hasn't started" as a separate analytic bucket; useful if you want to surface "WO waiting for IPQC > N min" as a leader-board metric. Same data is derivable from `setting.end_at` + first IPQC capture timestamp without a new state. |
| **Contract gap** | §3.1 transition grid (locked at P10.7a-2.3) lists both `SETTING → IPQC_WAIT` and `SETTING → SETTING_DONE → IPQC_WAIT` as forceable cells. The matrix is permissive — both paths compile. Locking direct closes 2 grid cells (`SETTING → SETTING_DONE` + `SETTING_DONE → IPQC_WAIT`) as **prohibited at runtime** (still forceable via admin). Amendment needed: §3.1 footnote stating runtime-direct-only. |

### Q2 — `WO_RUN_QTY_ADD` audit event granularity: per-tap or roll-up?

| | |
| --- | --- |
| **Recommendation** | **Per-tap** — every quantity entry produces one audit row. |
| **SpecHub citation** | `docs/06-mes-scan-product.md` line 162: "Add qty buttons: +100 / +500 / +1000 / custom · Add reject: +5 / +10 / +20 NG". Lines 174-178 list OEE math (`availability` / `performance` / `quality` / `OEE = a × p × q`) which depends on knowing WHEN each delta landed. SpecHub doesn't explicitly mandate per-tap audit but the OEE formulas can't compute `performance = qty_done / (planned_speed × run_time)` accurately if deltas are rolled up by minute. |
| **Trade-off** | **Per-tap** (recommended): forensic-grade audit trail — if a dispute arises ("operator claims 5000 units, customer says 4800"), the per-tap log shows every entry with timestamp + user. Volume is acceptable: 1 tap / 10 sec for an 8h shift = 2,880 rows / WO; SQLite handles this trivially. **Roll-up per minute** (alternative): one row per minute carrying `sum(delta_done) / sum(delta_ng) / first_ts / last_ts / N_taps`. Saves ~83% rows but loses per-tap user attribution (which OP entered which delta when 2 OPs share a shift). |
| **Contract gap** | §5.1 row-write contract has no `wo_qty_entry` row yet — entirely new in 7c-1. Locking per-tap shape (`QtyDoneDelta`, `QtyNgDelta`, `NgReasonCode?`, `NgNote?`, `EnteredBy`, `Ts`) needs §5.x amendment. **Suggested addition**: §5.2 `wo_qty_entry` table contract — append-only, no UPDATE/DELETE (matches SpecHub line 266 "Audit immutability: append-only constraint at DB level"). |

### Q5 — Counter editability: append-only delta or in-place edit?

| | |
| --- | --- |
| **Recommendation** | **Append-only negative delta** — operator submits `qty_done = -50` with a `WO_RUN_QTY_CORRECT` audit reason; current total auto-decreases. No edit-in-place. |
| **SpecHub citation** | `docs/06-mes-scan-product.md` line 266: "**Audit immutability**: append-only constraint at DB level (no UPDATE/DELETE GRANT to app role)". SpecHub doesn't explicitly call out counter corrections, but the principle extends — every state change is appended, never overwritten. Lines 162-164 only describe positive `+100/+500/+1000` and `+5/+10/+20 NG` quick-adds; corrections are inferred. |
| **Trade-off** | **Append-only negative delta** (recommended): forensic audit trail intact ("at 14:23 OP entered +500, at 14:24 entered -50 marked CORRECT because miscount"). DB invariant: `current_qty = SUM(QtyDoneDelta)` is always self-healing. Matches SpecHub immutability principle. **In-place edit** (alternative): UI simpler (one number on screen), operator fixes typos without thinking about deltas. BUT audit trail loses the "wrong → corrected" forensic depth; once row is UPDATE'd the original wrong value is gone. |
| **Contract gap** | New audit event `WO_RUN_QTY_CORRECT` needs to be reserved in §3.2 audit-event table alongside `WO_RUN_QTY_ADD`. Detail JSON carries `{original_intent: "correction", correction_reason: "…", linked_entry_id: <prior_id>}`. **Suggested addition**: §3.2 reserves `WO_RUN_QTY_ADD` + `WO_RUN_QTY_CORRECT` as a pair; controller validates `linked_entry_id` exists + belongs to same WO before accepting the negative delta. |

## 7. Risk assessment

- **Counter race** (two operators on same WO tap +100 simultaneously). Soak test N=10 must prove both deltas land in the ledger AND the cached `QtyDoneCached` reflects the sum. Same single-SaveChanges + tracked-query pattern as 7b-2 rollup.
- **PAUSED-while-stale-ETag**. Operator A pauses → operator B's UI ETag is stale → operator B's qty-add fires 409. Recommendation: same 7b-3 reload-on-409 pattern; banner "Đã tạm dừng — tải lại".
- **Concurrent setting timer**. Multiple `SettingStartAt` writes on race. Use `SettingStartAt is null` guard on the transition so only the first PREPRESS → SETTING write sets the timestamp.
- **Audit log volume**. Per-tap WO_RUN_QTY_ADD events at high run rates (1 tap / 10 sec for an 8-hour shift = 2,880 rows / WO). Acceptable for SQLite at our scale; revisit retention if production volumes grow 10×.
